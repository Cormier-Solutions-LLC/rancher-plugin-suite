# Snapshot and DNS management security rollout

The installed snapshot APIs require a Rancher session in the local cluster. Snapshot reads require access to the configured manager state and the backing inventory. Network snapshots contain cluster-wide inventory, so access requires cluster-wide list permission for the inventory resource types. Writes also require permission to update the configured manager state. The Kubernetes health probes use `/healthz`.

An operator must review and re-enable previously saved automatic snapshot and cleanup policies after the upgrade. Existing archives and their original unlock passwords continue to work. A protected network schedule records the exact Secret references the operator could read during review. A later capture stops before reading a newly referenced Secret until an operator reviews the schedule again.

The Windows DNS bridge verifies its active job through the dedicated snapshot verification endpoint. Install the updated `windows-dns-bridge.ps1`, the generated bridge RBAC, and the new snapshot runtime together. The bridge uses its existing credential to sign a short-lived proof for the job and snapshot. The verifier returns only the source identity and records required for that job.

1. Run `node scripts/prepare-snapshot-runtime.mjs` to generate the snapshot image build context. Build and publish it, set `SNAPSHOT_RUNTIME_IMAGE` to the published digest, and rerun the generator to create the manifests for both snapshot services.
2. Build the DNS readiness binary and run `node scripts/prepare-dns-runtime.mjs`. Issue the generated cert-manager CA and server certificates before moving traffic. Publish the public CA certificate as key `ca.crt` in the `dns-engine-client-ca` ConfigMap in both `dns-system` and `manager-system`. The CA private key stays in the issuing Secret. Distribute trust before rotating the CA.
3. Coordinate the DNS engine, controller, and snapshot service rollout. Use the DNS controller manifests from `node scripts/prepare-dns-controller.mjs`. The management API uses verified HTTPS on TCP 53443. Confirm each replica serves a certificate valid for its service hostname. Verify direct cross-pod access to the old HTTP port is blocked. The TLS sidecar uses HTTP on loopback inside the engine pod. Confirm retained Technitium settings allow that loopback connection.
4. Verify normal DNS queries on TCP and UDP 53, controller observation refresh, Rancher snapshot reads and writes, and the Windows bridge pre-change check. Confirm the saved policies are reviewed and re-enabled before relying on scheduled captures or cleanup.
